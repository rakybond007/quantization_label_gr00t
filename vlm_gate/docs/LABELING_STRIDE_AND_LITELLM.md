# allex 전량 라벨링: 경로·간격·확률가중합 결정 근거

2026-09-15. 모든 수치는 실측이다. 재현 명령은 각 절 끝에 있다.

## 1. LiteLLM 프록시로 Gemini 를 쓸 수 있다

사내 프록시(OpenAI 호환)를 통해 `gemini/gemini-3.8-flash` 를 쓴다.

```
키   ~/.config/litellm/key    (chmod 600, 레포에 넣지 않는다)
주소 ~/.config/litellm/base
판정기 scripts/allex_litellm_judge.py
```

**직결 Google API 와 판정이 같다.** 정답지 119청크에 같은 입력을 넣고 비교했다.

| | A | B | C | D | rho | AUC |
|---|---|---|---|---|---|---|
| 직결 평균 | 2.09 | 2.19 | 2.60 | 2.85 | +1.00 | 0.793 |
| 프록시 평균 | 2.03 | 2.24 | 2.63 | 2.87 | +1.00 | 0.796 |
| 답 일치 | 88% | 92% | 75% | 87% | | |

문항별 불일치는 프록시 탓이 아니다 -- temperature 0 에서도 사고 과정이
비결정적이라 직결을 두 번 돌려도 같은 정도로 흔들린다 (3절에서 정량화).
그래서 정답지로 맞춘 가중(A .70 / B .30 / C .80 / D .20)을 그대로 쓴다.

사고 억제는 `reasoning_effort: "low"`. 직결의 `thinkingLevel: "low"` 와 같은
자리이고 출력이 999 -> 19 토큰으로 준다. 완전히 끌 수는 없다.

### 비용과 처리율 (프록시가 헤더로 직접 알려준다)

```
x-litellm-response-cost: 0.0021615     호출당 $0.00216 (할인·마진 0)
usage: 입력 2787 (이미지 2178 + 글 609) · 출력 19
```

동시 요청을 올려도 실패가 없다.

| 동시 | 처리율 | 실패 |
|---|---|---|
| 4 | 0.43 req/s | 0 |
| 16 | 1.95 | 0 |
| 32 | 2.46 | 0 |
| 64 | **7.70** | 0 |
| 96 | 7.86 | 0 |

### 배치는 이 프록시로 못 쓴다 -- 그리고 쓸 필요가 없다

`create_batch` 가 `openai` 만 받는다. `gemini`/`anthropic`/`bedrock` 은
미지원, `vertex_ai` 는 프록시에 ADC 가 없다. Gemini 파일 업로드는 Google 로
나가면서 `API_KEY_INVALID` 로 죽는다.

배치는 반값이지만 직결 Google API 로 나가야 하고 완료까지 최대 24시간이다.
프록시 단건이 동시 64 로 **1.7시간**에 전량을 끝내므로 배치를 포기한다.
프록시는 회사 예산, 직결은 개인 키라는 점도 같은 방향이다.

주의: 이 가상 키는 `llm_api_routes` 만 허용돼서 `/key/info` 가 막혀 있다.
**예산 한도를 코드에서 알 수 없다.** 키 발급처에 확인해야 한다.

## 2. stride 16 에는 메울 사이 프레임이 없다

먼저 흔한 오해를 걷어낸다. **stride 16 은 청크 길이 16 과 같아서 청크가
빈틈·겹침 없이 타일링된다.**

```
CHUNK = 16, STRIDE = 16   (scripts/allex_v4_label.py)
청크 48,086 개가 769,376 / 771,862 프레임 = 99.68% 를 덮는다
남는 0.32% 는 에피소드 맨 끝 꼬리 (중앙 8프레임)
```

판정기는 프레임 f 의 한 점을 보지 않는다. `descriptors(A,WR,WL,f,16)` 이
f~f+15 를 보고 **그 청크에** 등급을 준다. 그 16프레임 전부가 그 라벨의
소유이므로 보간할 구간이 존재하지 않는다.

배달본은 이미 그렇게 만든다 (`scripts/allex_write_confidence_column.py`):

```python
v[f : f+16] = K                        # 청크 전체에 그 K 를 깐다 (hold = NN)
v[np.isnan(v)] = ch[last]              # 꼬리는 마지막 청크 값
v = np.convolve(v, np.ones(9)/9, ...)  # 경계 9프레임 완만화 (david 의 0.3s 램프)
```

램프는 정확도 장치가 아니다. K 가 재생속도로 소비되므로 계단으로 튀면 저크가
생긴다. 경계 단차가 평균 0.176 인데 그걸 9프레임에 펴 바르는 것뿐이다.

## 2b. stride 를 16 보다 성글게 하고 메우는 것은 안 된다

"돈을 아끼려고 stride 32 로 라벨하고 사이를 보간하면?" 의 답이다.
실제 stride 16 라벨 10487청크(에피 80)를 참값으로 두고, 성글게 라벨한 뒤
메운 지점만 평가했다.

성글게 라벨하고 사이를 메우면 얼마나 틀리는지, 실제 stride 16 라벨
10487청크(에피 80)를 참값으로 두고 측정했다. 메운 지점만 평가한다.

| 라벨 간격 | NN \|Δp\| | 선형보간 \|Δp\| | 에피평균 \|Δp\| | 역치 0.5 판정 뒤집힘 |
|---|---|---|---|---|
| stride 32 | 0.1765 | **0.1454** | 0.2193 | NN 21.0% / 보간 **17.4%** |
| stride 48 | 0.1767 | 0.1657 | 0.2223 | 20.9% / 21.3% |
| stride 64 | 0.1935 | 0.1734 | 0.2224 | 23.8% / 23.0% |

**보간이 에피평균보다 겨우 34% 낫다.** 즉 보간이 살려내는 정보가 거의 없다.

이것이 stride 16 을 하한으로 잡는 근거다.

원인: 이웃한 stride 16 청크끼리 p 가 이미 평균 0.1755 (중앙 0.1226) 벌어져
있다. 전체 p 표준편차가 0.2654 이므로 **16프레임 사이에 신호가 이미 66% 바뀐다.**
보간할 상관이 남아 있지 않다.

### 이 변동이 판정기 잡음이 아니라는 확인

"이웃 청크가 다른 게 장면 변화가 아니라 판정기가 흔들린 것뿐"이라면 보간이
잃는 건 잡음일 뿐이다. 그래서 **같은 청크를 두 번 판정한** 직결 vs 프록시
결과로 잡음을 재봤다.

```
판정기 자체 잡음     |Δconf| 0.0333   판정 뒤집힘  4.2%
stride32→16 보간     |Δp|    0.1454   판정 뒤집힘 17.4%   ← 잡음의 4.4배
```

보간 오차가 판정기 잡음의 4.4배다. **stride 16 의 변동은 실제 장면 변화이고,
보간은 진짜 정보를 지운다.** stride 16 보다 성글게 가지 않는다.

## 3. 확률가중합 conf 는 Gemini 로 불가능하다

`logprobs: True`, `logprobs+top_logprobs`, 구글식 `responseLogprobs` 셋 다
**HTTP 400** 으로 거부된다. Gemini 는 정수 등급만 준다.

**그래서 지금까지의 API 판정 실험은 전부 정수등급 conf 였다.** 확률가중합이
아니었다.

정수등급으로 충분한지 Cosmos 9179청크(gp 100% 실림)에서 두 방식을 비교했다.

| | 평균 | 표준편차 | 서로 다른 conf 값 |
|---|---|---|---|
| 정수등급 | 0.4956 | 0.1133 | **38개** |
| 기대등급(확률가중합) | 0.5050 | 0.0708 | 7469개 |

```
|Δconf| 평균 0.0498 · 95분위 0.1189 · 최대 0.2270 · 순위상관 +0.77
역치 0.45  통과 73.9% → 78.8%   뒤집힘 16.2%
역치 0.50  통과 57.7% → 49.7%   뒤집힘 23.9%
역치 0.55  통과 19.8% → 23.6%   뒤집힘  5.3%
```

문항 4개면 이론상 5^4=625 조합이지만 **실데이터에서는 38개만 쓰인다.**
계단이 실재한다. 역치를 촘촘히 못 돌린다.

결론: 확률가중합이 필요하면 로컬 Cosmos(logprob 있음)를 써야 한다.
Gemini 는 38단 계단을 감수한다. 다만 정답지 기준 판별력은 Gemini 가
Cosmos 보다 높다 (JUDGE_MODEL_COMPARISON.md: Gemini 0.865 vs Cosmos 0.754).
**계단이냐 판별력이냐의 교환이다.**

## 4. v1_v2 는 v1_v2_v3_v4 의 앞부분이다 -- 순서대로 하면 된다

```
v1_v2        에피 0~159 (160)  프레임 447,162
v1_v2_v3_v4  에피 0~319 (320)  프레임 771,862
  앞 160에피: 길이 일치 160/160 · tasks 일치 160/160 · 영상 md5 동일
  에피 160~319 는 v1_v2 에 없다 = v3_v4 증분
```

에피소드 번호 순서로 돌리면 0~159 가 끝난 시점에 그 자체로 완결된 v1_v2
라벨셋이 나오고, 160~319 를 이어 붙이면 v1_v2_v3_v4 가 된다.
**앞부분을 다시 돌릴 필요가 없다.**
