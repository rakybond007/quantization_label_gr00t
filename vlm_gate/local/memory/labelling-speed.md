# 라벨링이 느린 이유 — 잰 것 (2026-09-04)

디코딩을 앞서 하면 빨라질 거라 짚었는데 **틀렸다.** 학습 로더가
`dataloader_num_workers=8` + `persistent_workers` 를 쓰는 건 맞지만,
그건 변환 파이프라인이 무거운 학습 스텝 이야기고 라벨링은 사정이 다르다.

## 시간이 어디로 가나 (한가한 A100, 배치 8, 카메라 3장)

| | 초/프레임 | 비중 |
|---|---|---|
| decord 디코딩 | 0.0003 | **0.1%** |
| 전처리 `apply_chat_template` | 0.015 | 7% |
| `model.generate` | 0.19 | **93%** |
| 합 | **0.26** | |

- 생성은 **25토큰에서 EOS로 멈춘다.** `max_new_tokens=192` 는 낭비가 아니다.
- 93%는 전부 **프리필**이다 — 8건 × 카메라 3장 = 이미지 24장.
  배치 8→16 이 0.245→0.238 로 평평한 것도 이걸로 설명된다.

## 그래서 안 되는 것

- **디코딩 선행(프리페치): 최대 0.1%.** 하지 마라.
- **요청 파이프라이닝: 1~2%** (0.260 → 0.255, 스레드 2·3개 모두).
  클라이언트가 놀고 있다고 본 0.43초는 서버의 HTTP·base64 처리라
  어차피 생성과 직렬이다.
- 줄일 수 있는 건 이미지 수·해상도뿐인데 그건 라벨 자체를 바꾼다.

## 실제로 느렸던 이유

잡 155328 은 0.446 초/프레임 — 한가한 노드의 1.7배. 파이프라인 구조가
아니라 **노드를 나눠 쓰는 대가**다. GPU 사용률이 0↔100 을 오간다.

`OMP_NUM_THREADS` 를 안 걸면 torch 가 프로세스마다 코어 전부를 잡아,
판정 2개가 24코어에서 24스레드씩 요구하고 OMP 풀이 스핀대기한다
(155328 의 판정 둘이 각각 CPU 821%). **6으로 묶어도 속도는 그대로**
(0.258 대 0.257)라 `sbatch_phase9_alinlab.sh` 에 넣었다. 공짜 걸기다.

측정 도구: `vlm_gate/scripts/phase9_prefetch_test.py` (seq/pf/pp),
서버 쪽 분해는 `JUDGE_PROFILE=1`.
